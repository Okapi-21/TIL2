# メール関連知識整理（SPF / DKIM / DMARC）

> メール送信における送信ドメイン認証の仕組みを整理したメモ。
> Postfix + OpenDKIM 構成を前提とする。

---

## 外部DNS（外部向けDNS）に登録するレコード

以下の3つの認証方式は、内部IPから外部へメールが「**送信**」されるタイミングで、「**受信側**」から問い合わせを受けるものになる。
よって、内部DNSには不要なレコードであり、外部向けDNSにのみ登録する。

---

## SPF（Sender Policy Framework）

SPFとは簡潔にいうと「送信者のルールを定める仕組み」である。
具体的には、「このドメインのメールは、このIPアドレスから送られます」ということをDNSに宣言しておく仕組みのこと。

一般的なAレコードがIPとドメインの対応関係のみを示すのに対して、
SPFレコードはこのドメインでメールを送信してよいのは誰（どのIPか）か、**メールを送信するための権限**を示している。
そのため、SPFはメール送信の文脈のみで使用され、Webサイトへのアクセスやその他の通信には一切関係を持たない。

### 実際のレコード

```bash
example.ac.jp.  IN  TXT  "v=spf1 ip4:203.0.113.1 -all"
```

- `v=spf1`：SPFレコードとしての宣言
- `ip4:203.0.113.1`：このIPv4アドレスからの送信を許可
- `-all`：それ以外のIPからの送信は全て不正と見做して良い

`~all` と `-all` の違い：

| 記述 | 意味 | 用途 |
|------|------|------|
| `~all` | 許可IP以外は怪しいが、受け取っても良い（ソフトフェイル） | 初期導入時の検証期間 |
| `-all` | 許可IP以外は全て不正（ハードフェイル） | 運用が安定した後の本番設定 |

最初は `~all` で始めて、問題がないことを確認してから `-all` へ切り替えるのが一般的。

**SPFはPostfix側の設定は不要。** DNS側のレコード登録のみで完結する。

---

## DKIM（DomainKeys Identified Mail）

DKIMは直訳すると「ドメインの鍵で認証されたメール」という意味になる。
SPFがメールを送信するための権限を確認するための機能であったのに対し、
DKIMは**メールの内容が改竄されていないか確認する**ための機能である。

### DKIMの仕組み

DKIMでは「秘密鍵」と「公開鍵」の2つの鍵をペアで使用する。

- **秘密鍵**：Postfixサーバの中に保管する。外部には絶対に非公開とする。
- **公開鍵**：外部向けDNSに登録する。誰でも確認することができる。

秘密鍵で署名したものは公開鍵でしか検証することができないので、以下のような流れでメール内容の真正性を担保している。

> **DKIMの検証フロー**
>
> ① メール送信時に「秘密鍵」でメール内容のハッシュに署名
> ② メール受信側が外部DNSに問い合わせ、「公開鍵」を入手してハッシュを検証
> ③ ハッシュ値が一致 → メールは改竄されていないと判断
> 　 ハッシュ値が不一致 → メールが途中で改竄された、または偽物であると判断

SPFとの違いは、**DKIMはPostfix側にも設定が必要**というところ。

### Postfix側の設定

#### 1. OpenDKIMのインストールと設定

DKIMの署名処理はPostfix本体ではなく、OpenDKIMという別のソフトウェアが担う。
Postfixがメールを送信する直前にOpenDKIMが署名をつける、という連携になる。

鍵ペアの生成：

```bash
opendkim-genkey -d example.ac.jp -s selector01
```

設定ファイル（`/etc/opendkim.conf`）で以下の項目を主に設定する：

| パラメータ | 設定内容 |
|-----------|---------|
| Domain | 署名対象ドメイン |
| KeyFile | 秘密鍵のファイルパス |
| Selector | セレクタ名（例：selector01） |
| Mode | s（署名のみ） |

### セレクタについて

セレクタとは鍵を識別するための名前で、鍵を更新したいときに用いる。
セレクタがあることで、新旧の鍵を共存させながら段階的に切り替えることが可能になる。

### keyTable, SigningTable について

KeyTableはDKIMレコードと秘密鍵の関連付けるための記述

```bash
#[セレクタ名]._domainkey.[ドメイン名]　[ドメイン名]:[セレクタ名]:[秘密鍵までのパス]
#default._domainkey.example.com example.com:default:/etc/opendkim/keys/default.private
```

SigningTableはメールアドレスと秘密鍵を関連付けのために記述が必要

```bash
# *@[ドメイン名] [セレクタ名]._domainkey.[ドメイン名]
# *@example.com default._domainkey.example.com
```

KeyTableとSigningTableは複数ドメインを使用する際に定義が必要

#### 2. PostfixとOpenDKIMの連携設定

Postfixの `main.cf` に、OpenDKIMを経由する設定（milter設定）を追加する：

```bash
# SMTP経由で受け取ったメールに対して、milterを適用
smtpd_milters = inet:localhost:8891

# SMTP経由以外（sendmailコマンド等）で受け取ったメールに対しても、milterを適用
non_smtpd_milters = inet:localhost:8891

# OpenDKIMが何らかの理由で応答しなかった場合の動作
milter_default_action = accept
```

`milter_default_action` の選択肢：

| 値 | 動作 | 特徴 |
|----|------|------|
| `accept` | 署名なしで送信を継続 | メール到達性を優先 |
| `reject` | メール送信を拒否 | セキュリティを優先 |
| `tempfail` | 一時的なエラーとして後で再試行 | バランス型 |

### 外部DNS側の設定

公開鍵の内容をTXTレコードとして登録する：

```bash
selector01._domainkey.example.ac.jp.  IN  TXT  "v=DKIM1; k=rsa; p=MIGfMA0GCSqGSIb3DQEBA..."
```

- `selector01._domainkey.example.ac.jp`：レコード名。受信側はここに問い合わせを行う。
- `v=DKIM1`：DKIMのレコード宣言
- `k=rsa`：暗号方式（RSA）
- `p=xxxxxxxxx`：公開鍵の本体（長い文字列）

## DMARC（Domain-based Message Authentication, Reporting and Conformance）

直訳すると「ドメイン単位のメール認証・報告・準拠の仕組み」という意味になる。
SPF、DKIMはそれぞれ単独でメールが本物かを検証する仕組みだが、
SPF、DKIMだけでは**検証に失敗したメールをどう扱うか**が不明な状態となってしまう。
この判断基準を示すものがDMARCである。
つまり、DMARCは**SPFとDKIMの検証結果を受けて、最終的な判断を下すためのポリシー**のこと。

### 実際のレコード

```bash
_dmarc.example.ac.jp.  IN  TXT  "v=DMARC1; p=none; rua=mailto:dmarc-report@example.ac.jp"
```

- `_dmarc.example.ac.jp`：DMARCは必ず `_dmarc.` で始まる
- `v=DMARC1`：DMARCレコード宣言
- `p=none`：ポリシー
- `rua=mailto:...`：レポート送信先メールアドレス

### ポリシーの段階

| ポリシー | 動作 | 用途 |
|---------|------|------|
| `p=none` | 何もしない（レポートのみ） | 初期導入時。設定ミスの検知に使う |
| `p=quarantine` | 迷惑メールフォルダに隔離 | 中間段階 |
| `p=reject` | 完全拒否 | 運用安定後の最終形 |

一般的には上から順に厳しくしていく。最初から `reject` にしてしまうと、設定ミスに気づくことができない。

**DMARCはSPFと同様に、Postfix側の設定は不要。** DNS側のレコード登録のみで完結する。

## 3つの認証方式の比較まとめ

| 認証方式 | 何を確認するか | Postfix側の設定 | 外部DNS側の設定 |
|---------|--------------|----------------|----------------|
| SPF | 送信元IPが正当か | 不要 | SPFレコード（TXT）登録 |
| DKIM | メールが改竄されていないか | OpenDKIM導入＋秘密鍵で署名 | 公開鍵レコード（TXT）登録 |
| DMARC | SPF/DKIM失敗時のポリシー | 不要 | DMARCポリシー（TXT）登録 |

3つとも確認するのは**受信側（Gmail、Outlook等）**であり、確認時に問い合わせるのは**外部向けDNS**。
内部DNSは外部からアクセスできないため、SPF/DKIM/DMARCレコードの登録は不要。

## おまけ：Squid（プロキシ）

Squidは簡潔に表現すると、内部PCがインターネットにアクセスする際の代理サーバ（プロキシ）である。
内部PCは直接インターネットに出ず、必ずSquidを経由する構成となっている。

### メリット

**1. セキュリティ（内部PCを外部から隠すことができる）**

Squidがない場合、内部の各PCが直接インターネットに通信するので、インターネット側から見ると大量の内部PCが個別に見えてしまう。
Squidがある場合、インターネットに出ていくのはSquidだけなので、外部から見えるのはSquidのIPアドレスだけになる。

**2. ログ（誰がどこにアクセスしたか記録できる）**

組織として、ネットワークから何にアクセスされたのかを記録しておく必要がある場合がある。
Squidを経由させることで、すべてのアクセス記録がSquid上に残る。

**3. キャッシュ（同じページへのアクセスを高速化）**

Squidはキャッシュサーバとしての役割を果たすこともあるが、最近のWebサイトはHTTPSが主流のため、Squidでキャッシュできないケースも増えている。
