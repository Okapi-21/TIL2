### Infrastructure as Code (Iac) 

　Infrastructure as Code とは、インフラの構成をコードで管理する考え方のこと、サーバーやネットワーク、データベースなどの設定をテキストファイルに書き、それをバージョン管理することで、誰がいつ何を変更したのかが追跡できるようになる。
　Iacの対義語は、webコンソールから手動でぽちぽち操作する「クリック運用」。
クリック運用は手軽だけれど、設定の経緯が記録されない、同じ環境を再現するのに手順書が必要になる、誰かが知らない間に設定を変えてしまう、と言った問題が起きやすくなる。IaCを導入すると、これらの問題が一気に解決し、インフラがアプリケーションコードと同様に、レビュー・テスト可能な対象となる。

#### 宣言型

　宣言型とは「最終的に存在しておいて欲しい状態」を記述するスタイル。
例えば、「t3.microのEC2インスタンスを１台、東京リージョンに存在させる」と書くと、Terraformが現状との差分を計算し、必要なら作成、すでに実在している場合は何もしない、という判断を自動で行ってくれる。

#### 手続き型

　「どうやって作るか」の手順を１行１行記述するスタイル。シェルスクリプトのように上から順に実行される為、すでに存在する場合のスキップなどは自分で書く必要がある。

ex)

```tf
# プロバイダーの設定（どのクラウドを使用するのか）
provider "aws" {
  region = "ap-northeast-1"
}

#　変数の宣言
variable "project_name" {
  type = string
  default = "learning"
}

#　ローカル値の宣言
locals {
  tags = {
    project = var.project_name
  }
}

# リソースの宣言
resource "aws_vpc" "name" {
  cidr_block = "10.0.0.0/16"
  tags = local.tags
}

# 出力値の宣言
output "vpc_id" {
  value = aws_vpc.main.id
}
```



#### 基本コマンド

`terraform init`：最初に一度だけ実行するコマンド、実行することで terra form が 必要なプロバイダーのプラグインをダウンロードしてくれる。
　　　　　　　　　`.tf`ファイルを編集して、プロバイダーを追加した後にも改めて実行する必要がある。

`terraform plan`：現在のインフラと `.tf`の差分を計算し、これから何が作られ、何が更新され、何が消えるのかを表示してくれる。
　　　　　　　　　実際の変更はまだ加えない為、何度実行しても安全、
　　　　　　　　　レビュー前に必ず `plan` を実行し、想定通りの差分となるか確認したほうが良い

`terraform apply`： `plan`で出た差分を実際に適応するコマンド

`terraform destroy`： `.tf` で管理されているリソースを全て削除するコマンド、学習サイクル終わりに必ず実行し、不要な課金を残さないようにする

##### 補助的なコマンド

`terraform fmt` ：ファイル整形

`terraform validate` ：構文エラー確認



#### tfstate の役割

tfstate は「現在の実際の状態」を保持している。

`apply` するときの Terraform の挙動はこのような流れになっている。

1. tfstateを読み込み、「現在の状態」を把握
2. `.tf`を読み込み、「あるべき姿」を把握
3. 両者の差分を計算し、必要な変更を生成する
4. 変更を実行し、tfsateを更新

つまり、tfstateを失うと、Terrafromは「今のインフラの状態」を見失ってしまう。
これは事故のもとになる為、本番運用では tfstate をリモートに保存し、複数人で共有できるように設定するのが定石である。
学習中はローカルの `terraform.tfstate` で十分だけれど、リモート保存の存在は頭に入れておいたほうが良い



#### 依存関係と繰り返し

Terraformは、リソース同士の依存関係を自動で解決してくれる。

例えば、`aws_subnet`の中で、`aws_vpc.main.id`のように別のリソースを参照すると、terraformは「サブネットはVPCに依存する」と理解し、先にVPCを作ってからサブネットを作るという順序を自動で組み込んでくれる。これを「**暗黙の参照**」と呼ぶ。

ただし、コード上は参照していないけれど、作成順序を整除したいこともあると思うので、その時は `depends_on` で明示的に示す必要がある。

複数のリソースを一度に作る場面では、`count` と `for_each` が有効
`count` は数字を指定して同じリソースを N 個作るのに対し、`for_each` はマップやセットを渡して鍵ごとに別々の設定でリソースを作れる。
サブネットを 2 つの AZ に作る、といった場合は `for_each` がよく使われる。



#### リソース置換の制御

リソース更新するとき、Terraformは「破棄して作り直し」を選択することがある。
これがダウンタイムに繋がると困る場面では、`lifecycle`ブロックの `create_before_destroy = true` を指定して、
「先に新しいリソースを作ってから古いリソースを消す」と言ったような順序に変更することが可能になる。
